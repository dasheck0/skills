# Contributing to dasheck0/skills

Thanks for improving this skill library. This document covers how to add a new skill, update an existing one, and the conventions every contribution must follow.

---

## Commit Messages — Conventional Commits (MANDATORY)

Every commit to this repository **must** follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). This applies to manual commits and to commits generated by AI assistants (e.g. via the `skill-updater` skill) alike.

Format:

```
<type>(<optional scope>): <description>
```

Allowed types:

| Type | When to use |
|------|-------------|
| `feat` | New skill, or a new capability added to an existing skill |
| `fix` | Bug fix in a skill's instructions or behavior |
| `docs` | Documentation-only change (README, CONTRIBUTING, comments) |
| `chore` | Tooling, repo config, non-skill maintenance |
| `refactor` | Restructuring a skill without changing its behavior |
| `test` | Adding or updating evals |

Examples:

```
feat(skills): add architecture-interview
fix(skill-installer): correct sparse-checkout path
docs(readme): add conventional commits section
refactor(skill-updater): simplify diff output formatting
```

For changes touching multiple skills, list them in the description:

```
feat(skills): update skill-installer, skill-updater
```

**No exceptions.** Commits that don't follow this format will be asked to be amended before merge.

## Adding a New Skill

### 1. Directory structure

```
skills/
└── your-skill-name/       # kebab-case, no prefix
    ├── SKILL.md            # required
    ├── scripts/            # optional: helper scripts
    ├── evals/              # optional: eval configs
    ├── rules/              # optional: externalized rules
    └── LICENSE.txt         # optional
```

**Naming:** skill directories are always `kebab-case`, without any prefix (no `nv-`, no `my-`, etc.).

### 2. SKILL.md structure

Every `SKILL.md` starts with a YAML frontmatter block:

```yaml
---
name: your-skill-name
description: >
  Text describing when this skill should trigger. This text is used by the
  AI assistant to automatically recognize and load the skill. Include
  concrete trigger phrases (English + any other relevant language) here.
license: MIT
metadata:
  author: your-name
  version: '1.0.0'
---
```

The actual skill content — instructions, workflows, examples, references — follows as Markdown after the frontmatter.

#### Frontmatter fields

| Field | Required | Description |
|-------|----------|-------------|
| `name` | ✅ | Unique identifier, must match the directory name |
| `description` | ✅ | When should the skill trigger? The more concrete, the better |
| `license` | – | License (e.g. `MIT`) |
| `metadata.author` | – | Skill author |
| `metadata.version` | – | Semver version |

### 3. Vercel Labs Skills CLI compatibility

This repository is a source for `npx skills@latest`, so every publishable skill
must comply with the Agent Skills discovery format:

- Keep publishable skills in `skills/<skill-name>/SKILL.md`; do not put them only
  under tool-specific folders such as `.opencode/skills/`.
- The `name` must exactly match the directory name, be 1–64 characters, and use
  lowercase letters, numbers, and single hyphens only.
- `description` is required, non-empty, and must not exceed 1,024 characters.
- Keep optional resources inside the skill directory (for example `scripts/`,
  `references/`, `assets/`, `evals/`, or `rules/`) so the CLI can install them with
  the skill.
- Before opening a PR, run `npm test`. It validates every `skills/*/SKILL.md`.
- To confirm CLI discovery without modifying an installation, run
  `npm run verify:skills-cli` from the repository root.

Users can then install an individual skill with:

```bash
npx skills@latest add dasheck0/skills --skill=your-skill-name
```

### 4. What makes a good skill?

- **Clear `description`**: The assistant decides relevance based on this field. Concrete trigger phrases (including casual phrasing) significantly improve match rate.
- **Focused**: One skill solves exactly one problem. Prefer two small skills over one large one.
- **Reproducible**: The skill should be deterministic — same input, same output.
- **Self-contained**: Don't assume dependencies on other skills that aren't in this repo.

### 5. Submitting

**Recommended:** use the bundled `skill-updater` skill — it detects locally installed skills, diffs against the remote repo, pushes on your confirmation, and automatically adds the new skill to the README table.

**Manual:**
1. Create a branch: `git checkout -b skill/your-skill-name`
2. Add your skill under `skills/your-skill-name/`
3. Test it locally with `npm test` and `npm run verify:skills-cli`
4. Commit using Conventional Commits (see above)
5. Open a PR against `master`

## Updating an Existing Skill

Same process as adding a new skill, minus the README update (only new skills get a README entry). Use `fix:` or `refactor:` as the commit type depending on whether you changed behavior or just restructured.

---

## Review Checklist (self-check before opening a PR)

- [ ] Skill directory is `kebab-case`, no prefix
- [ ] `SKILL.md` has valid YAML frontmatter with `name` + `description`
- [ ] `name` exactly matches its directory and meets Agent Skills naming rules
- [ ] `npm test` passes
- [ ] `description` includes concrete trigger phrases
- [ ] Commit messages follow Conventional Commits
- [ ] New skill is reflected in the `README.md` skill table (if not using `skill-updater`, which does this automatically)
